# Architecture Decisions

| ID | Decision | Reason |
|---|---|---|
| D-001 | 8 modules. React is built in slices, PostgreSQL and RAG are separate modules, and LangGraph comes after a plain Python pipeline. | Each module is testable, and workflow bugs are separable from logic bugs. |
| D-002 | JSON metadata behind a `DatasetRepository` interface until Module 6, then PostgreSQL. | Keeps the database out of the way until the core workflow works. |
| D-003 | Unsupported and insufficient-data answers return HTTP 200 with a `status` field. Query responses include `validation`, `assumptions`, `calculation_method`. | These are valid requests we cannot answer, not client errors. Also fixes the TDD's missing "validation status". |
| D-004 | ~~Frontend is Vite + React with JavaScript (`.jsx`).~~ **Superseded by D-019.** | Originally chosen to match the TDD and keep things simple for a beginner. |
| D-005 | `dataset_id` is a UUID string everywhere. Malformed returns 422, unknown returns 404. | The TDD examples (`dataset_001`) contradicted its own database design. |
| D-006 | Route functions are plain `def`, not `async def`. | Pandas and Gemini calls block. FastAPI runs `def` routes in a thread pool. |
| D-007 | LangChain is used minimally (embeddings/LLM interface). Vector search is our own SQL against `knowledge_documents`. | LangChain's PGVector store creates its own tables and conflicts with the TDD schema. |
| D-008 | Gemini failure fallbacks: rule-based classifier and template explanation. | Reliability, cheaper tests, fewer LLM calls. |
| D-009 | Gemini output must validate against a Pydantic `QueryPlan`, and column names are checked against an allowlist. | Prevents prompt injection and invented columns. |
| D-010 | Dataset profile is computed on demand from the CSV. | The `dataset_columns` table only stores summary data. |
| D-011 | Separate `backend/Dockerfile` and `frontend/Dockerfile`, one `docker-compose.yml`, PostgreSQL via the `pgvector/pgvector` image. | One Dockerfile cannot serve three services. |
| D-012 | RAG is the last V1 feature (Module 7). METRIC_DEFINITION uses a stub until then. | The TDD contradicted itself on V1 vs V1.5 for RAG. |
| D-013 | Settings via pydantic-settings. `CORS_ORIGINS` is a comma-separated string. | Avoids the JSON-list-in-env-var pitfall. |
| D-014 | `data/samples/` is committed. `data/uploads/` contents are git-ignored. | Sample data is shared, user uploads are private. |
| D-015 | No authentication in V1. Local and portfolio use only. | Explicitly out of scope in the TDD. |
| D-016 | `/health` returns `app`, `version`, `environment` in addition to `status`. | Useful for debugging, harmless to expose. |
| D-017 | Virtual environment lives at `backend/.venv`. `requirements.txt` is generated with `pip freeze`. | Reproducible installs. |
| D-018 | Line endings are LF via `.gitattributes`. | Prevents CRLF problems in Docker scripts later. |
| D-019 | Frontend is Vite + React + **TypeScript** (`.tsx` for components and pages, `.ts` for services, types and utilities). JavaScript will not be reintroduced. A `frontend/src/types/` folder will mirror the backend Pydantic schemas. Supersedes D-004. | Chosen by the developer. Type safety across the API boundary catches contract mismatches at build time. |
| D-020 | Module 2 accepts **CSV and `.xlsx`**. `.xlsx` support reads the **first worksheet only** and converts it to CSV at upload time, so every later module reads only `data/uploads/{dataset_id}.csv`. `.xls` and `.xlsm` files are rejected. The original `.xlsx` is not kept, and formula cells use their last saved value. Limits on file size, rows and columns are enforced (initial defaults: 10 MB, 100,000 rows, 100 columns, all configurable in `backend/.env` and confirmed at the start of Module 2). A warning is returned if a workbook has more than one sheet. Extends TDD FR-01, which specifies CSV only. | The TDD's problem statement says users keep data in "Excel or CSV files". Converting at upload keeps profiling, tools and the workflow unchanged. `.xlsx` is a zip archive that can expand enormously, so row and column limits are needed, not just a file-size limit. `.xls` and `.xlsm` add legacy-format and macro risks. |
| D-021 | Dataset preview: `GET /datasets/{id}/preview` returns the first **5 rows** by default (`rows` query parameter, hard maximum **20**). Long cell values are truncated (initial default: 100 characters), missing values are returned as `null`, and no internal file path is returned. Preview data is **never sent to Gemini** or any other LLM. Preview shows column names, sample rows, and row and column counts only. Types, missing values, duplicates and statistics belong to the Module 3 profile. | The user needs to confirm the right file was uploaded, but TDD §19 and FR-02 say not to expose raw data unnecessarily. A small, capped, separate endpoint balances both. |
| D-022 | Module 2 uses Python's built-in `csv` module and `openpyxl`, not Pandas. Pandas is added in Module 3, where it reads the clean CSV. | Row-by-row streaming lets limits stop huge files early, and every value stays exact text (for example `007`). Fewer dependencies in this module. |
| D-023 | Every error uses `{"error","code","details"}`. Statuses: 400 for bad file content, 413 for too large, 404 for unknown dataset, 422 for a bad dataset id, bad `rows` value or invalid request, 500 for unexpected errors (safe generic message, details only in logs). Codes are listed in `core/errors.py`. | Implements the TDD error format and fixes the known Module 1 issue. |
| D-024 | Storage per dataset: `data/uploads/{dataset_id}.csv` (clean UTF-8 CSV) and `{dataset_id}.meta.json`. The file path is never stored or returned. It is calculated from the UUID. The client filename is sanitised and used for display only. Files are written to a temporary name first and then renamed. | Path traversal protection. A failed upload leaves no half-written files. |
| D-025 | CSV encoding: UTF-8 (BOM allowed). If that fails, Windows-1252 is used and a warning is returned. UTF-16 and binary content are rejected. Only comma-separated files are supported, with a helpful error for `;`, `|` or tab. | Excel on Windows often saves Windows-1252 CSV. Silent guessing is avoided by warning. |
| D-026 | Table rules: blank rows are ignored, trailing blank columns are trimmed, header names are trimmed and must be unique ignoring case, short rows are padded, a row with more values than headers is rejected. Upload status is `uploaded` (Module 3 will set `processed`). Field names are `row_count` and `column_count` (the TDD example used `rows` and `columns`). | Predictable clean data for later modules. Consistent naming in backend and frontend. |
| D-027 | Preview `rows` above the maximum, or below 1, is rejected with 422 `INVALID_PREVIEW_ROWS`. It is not silently reduced. | The caller always knows exactly what they received. |
| D-028 | Docker is deferred to Module 6, together with Docker Compose and the upload volume. It was planned for Module 2, but it was not part of the Module 2 scope and I could not test Docker while preparing this module. | Avoids giving an untested Docker file. Module 6 needs Compose anyway for PostgreSQL. |
