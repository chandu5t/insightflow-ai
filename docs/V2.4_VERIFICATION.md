# V2.4 Verification Layer

## Purpose and boundary

V2.4 is a deterministic verification service after the V2.3 multi-agent workflow:

```text
V2.2 AnalysisPlan → V2.3 MultiAgentResult → V2.4 VerificationResult
```

It validates and inspects results; it does not execute analysis. `POST /analysis/verify` is additive. The existing V1 `POST /analysis/query`, V2.2 `POST /analysis/plan`, and V2.3 `POST /analysis/multi-agent` contracts remain separate and unchanged. Verification is not an agent and does not alter the V2.3 graph or its three-agent registry.

## Request and result schemas

`VerificationRequest` accepts a V2.2 `analysis_plan`, the serialized V2.3 result as `multi_agent_result`, and an optional `dataset_id` when dataset-level verification is needed. The V2.3 result is accepted as raw structured JSON so schema validation occurs inside the verifier and malformed results can return a structured `invalid_result_schema` outcome.

`VerificationResult` contains:

- overall `status`: exactly `passed`, `failed`, or `unsupported`;
- individual `checks`, `failed_checks`, and `unsupported_checks`;
- `verified_steps`, evidence references, structured errors, and metadata;
- a verification version, request ID, and fixed absolute tolerance metadata.

Overall status precedence is deterministic: any failed applicable check means `failed`; otherwise any required unsupported check means `unsupported`; otherwise `passed`. `failed_checks` contains only failed checks. Unsupported checks remain explicit and separate.

## Verification checks

1. **Schema validation:** validate the serialized result against the V2.3 `MultiAgentResult`/`AgentResult` schemas and required serialized fields. This runs first. Invalid structure returns `failed` with `invalid_result_schema`; dependent checks do not run. The verifier does not repair or infer fields.
2. **Plan/execution consistency:** compare planned and executed step IDs, operation identity (`AgentResult.metadata.operation`), step status, plan order, and declared dependencies. `depends_on` is the only dependency source; `inputs` is not interpreted as step IDs. A dependency must exist and be completed before its dependent executes. Hidden data flow is not inferred.
3. **Numerical verification:** independently recalculate only the frozen V2.3 scope: `count` without a column or named inputs (for a root dataset step), eligible `distinct_count` (root dataset step with a matching column input and no missing values), and `calculate_difference` from two successful dependency values using left minus right. Other undefined or unavailable numerical checks return `unsupported` with `verification_semantics_undefined`. Count operations with dependencies and other contexts that cannot be independently reconstructed are unsupported.
4. **Evidence/grounding:** inspect only `MultiAgentResult.final_result` and successful, non-null result payloads present in `MultiAgentResult.agent_results`. A non-null final result must equal a successful structured agent result to pass grounding. Each surfaced result is referenced by agent/step. The verifier does not inspect natural-language prose or invent claims.
5. **Consistency:** check explicitly represented workflow/step status consistency, including a completed workflow with incomplete or failed steps. Unusual values and undefined mathematical relationships are not treated as contradictions.

## Tolerance and data access

Floating-point comparisons use the fixed absolute tolerance `1e-9` (relative tolerance is zero). Exact non-floating comparisons remain exact. Tolerance is not configurable.

When an independent calculation requires dataset data, verification receives `dataset_id` and uses the existing `DatasetRepository` and `load_dataframe` path. This preserves V2.3’s cleaned-CSV interpretation and adds no storage infrastructure. Missing required context produces an explicit unsupported check.

## Failure categories and safe failure

Structured categories are `invalid_result_schema`, `plan_execution_mismatch`, `numerical_mismatch`, `unsupported_claim`, `consistency_violation`, `verification_semantics_undefined`, and `verification_failure`. Unexpected verifier exceptions produce `verification_failure`; they cannot produce a pass. Undefined semantics or unavailable required evidence/context are unsupported, never guessed or silently skipped.

## Tests and limitations

Focused tests cover the schemas, API, plan/execution and dependency checks, numerical checks and tolerance, grounding, consistency, failure handling, and V2.3 route compatibility. Regression runs and their exact results are recorded in [V2.4_COMPLETION_CHECKLIST.md](V2.4_COMPLETION_CHECKLIST.md).

Numerical coverage is intentionally narrow. The operation registry defines operation identity, not execution semantics. The verifier does not numerically validate transformations outside the frozen scope, does not prove hidden internal data flow, and does not assess arbitrary external text.

## Explicit non-goals and V2.5 boundary

V2.4 adds no verification agent, LLM judge, retry, self-correction, replanning, correction loop, arbitrary Python/code/shell/SQL execution, new database/vector infrastructure, planner change, Supervisor redesign, V1 workflow change, visualization, benchmark framework, or significance testing.

V2.4 ends at **Execute → Verify → Report**. V2.5 owns any future correction and re-execution loop.
