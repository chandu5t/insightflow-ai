# V2.5 Self-Correction

## Purpose and boundaries

V2.5 adds a bounded, deterministic correction endpoint around the existing V2.2 planner, V2.3 multi-agent workflow, and V2.4 verification service. It does not alter their routes or behavior. V2.5 creates no agent, execution engine, persistence layer, or model-based correction path.

```text
V2.2 AnalysisPlan
    ↓
V2.3 MultiAgentResult
    ↓
V2.4 VerificationResult
    ↓
V2.5 eligibility and correction
    ↓
V2.2 validation → V2.3 re-execution → V2.4 re-verification
```

## Approved strategy

The registry contains only `reconcile_single_step_id_mismatch`. It may correct only `analysis_plan.steps[0].step_id`, changing planned ID `P` to executed ID `E`. It preserves the original request and plan and records both the input and corrected plan.

The strategy requires all of the following structured evidence:

1. Exactly one V2.2 planned step exists with ID `P`, and it has no dependencies.
2. Exactly one completed executed step exists with ID `E`; `P != E`.
3. Exactly one successful Analysis Agent result exists for `E`.
4. That result's `metadata.operation` matches the planned operation.
5. The initial V2.4 result is `failed` and contains exactly three failed checks: `unexpected_executed_steps` for `E`, `planned_step_coverage` for `P`, and `workflow_step_consistency` for `P`.
6. The only unsupported check is `planned_step_status`, category `verification_semantics_undefined`, for `P`.
7. No additional failed or unsupported checks exist; the failed/unsupported lists agree with the individual checks.
8. The planned ID is absent from the execution status map, linking the unsupported status check to the same `P != E` mismatch.

The unsupported check remains unsupported. V2.4 gives failed checks precedence in the overall status, so this qualifying result is overall `failed`; V2.5 does not convert, override, or reinterpret the individual unsupported check. Any other unsupported initial result is terminal. Any unsupported check or result after re-execution is terminal, and the initial exception is never reused.

## Correction lifecycle and budget

The initial `passed` result terminates as `not_corrected` / `already_verified` with zero attempts. Initial overall `unsupported` terminates as `unsupported` / `verification_unsupported`. A failed result that does not meet every eligibility condition is uncorrectable; no budget is consumed. A qualifying result with budget zero terminates as `budget_exhausted`.

The accepted budget is 0–2, default 1. One attempt is counted after V2.3 re-execution is attempted. The sole strategy's unsupported-check exception is initial-only; a later V2.4 unsupported result terminates immediately. A later failed result without a newly supported strategy terminates as uncorrectable rather than looping.

Every attempt records its trigger, strategy, eligibility evidence, input/corrected plan, V2.3 result, V2.4 result, status, and safe error information. The original question, dataset ID, plan, execution, and verification remain in the response for traceability.

## Existing service integration

- **V2.2:** `validate_plan` validates the copied corrected plan before execution.
- **V2.3:** V2.5 builds the existing `MultiAgentRequest` and calls `run_multi_agent_workflow` with the injected dataset repository and metric retriever.
- **V2.4:** V2.5 calls `verify_execution` with the corrected plan, new V2.3 result, repository, and unchanged dataset ID.

The V2.5 endpoint reuses the existing FastAPI dependency providers for repository and retriever access. It adds no database or dataset infrastructure.

## API

`POST /analysis/correct` accepts the original `question`, `dataset_id`, `analysis_plan`, `execution_result`, `verification_result`, and `correction_budget`. It returns a structured terminal status, original/final artifacts, attempts, errors, and trace metadata. Existing V1–V2.4 endpoints remain unchanged.

Terminal statuses include `not_corrected`, `corrected`, `unsupported`, `uncorrectable`, `correction_failure`, `correction_validation_failed`, `re_execution_failure`, `budget_exhausted`, and `self_correction_failure`.

## Safety and limitations

V2.5 does not use an LLM to decide or perform a correction. It does not execute generated code, Python, shell, SQL, or arbitrary tools; change raw data; modify V2.2–V2.4 semantics; or perform retries outside the bounded correction lifecycle. The single strategy only reconciles a structural identifier mismatch and does not infer analytical intent.

V2.5 performs software orchestration only. It does not establish research hypotheses, report benchmark results, or implement V2.6 visualization or V2.7 evaluation. Correction success must not be presented as evidence of research improvement.
