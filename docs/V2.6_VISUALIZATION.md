# V2.6 Visualization

## Scope and architecture

V2.6 adds a deterministic visualization endpoint and fixed React/SVG renderers over existing V2.2 plans, V2.3 execution results, V2.4 verification outcomes, and optional V2.5 correction responses. It does not load datasets, recompute analytical results, verify results, correct plans, or use an LLM.

The additive endpoint is `POST /analysis/visualize`. The API accepts `question`, `dataset_id`, `analysis_plan`, `execution_result`, `verification_result`, and optional `correction_result`. Artifact fields are validated by the V2.6 service so malformed artifacts return the V2.6 structured response model.

When correction is absent, the supplied plan, execution, and verification form the candidate source set. When correction is present, only `final_plan`, `final_execution_result`, and `final_verification_result` are used for visualization. The top-level originals must agree with the correction response's original artifacts. Question and dataset ID must agree. Inconsistent artifacts fail closed.

Generation requires structurally valid, mutually consistent artifacts and an authoritative V2.4 verification status of `passed`. With correction, the terminal status must be `corrected` or `not_corrected`, and final verification must be `passed`. A valid but unsuitable status returns `unsupported`; malformed or inconsistent artifacts return `failed`.

## Supported charts and deterministic selection

The controlled chart types are `bar`, `line`, `pie`, and `scatter`. If multiple forms are possible, precedence is: explicit-evidence pie; explicit temporal or ordered line; scatter when at least two numeric variables and no categorical dimension are available; otherwise categorical bar. Pie/line/bar selection for categorical data follows that order. No chart type is inferred from natural-language question wording.

- **Bar:** Uses existing categorical/numeric pairs. All supplied rows are preserved; there is no aggregation, filtering, or inferred top/bottom-N.
- **Line:** Requires at least two observations with monotonic ISO date/time values or structured result ordering established by the plan's sort/rank ancestry. Arbitrary category labels are not treated as time.
- **Scatter:** Uses two numeric fields from the same supplied rows. It does not join, manufacture pairs, compute correlation, or add regression.
- **Pie:** Requires explicit `part_to_whole` evidence already present in a V2.2–V2.5 artifact. Numeric pairs or their apparent sum are insufficient. The accepted structured marker has `whole_id`, positive `whole_value`, `relationship: "components_of_whole"`, `category_field`, and `value_field`, located in analysis-agent metadata or in the structured result. The selected category/value fields must match the marker, all values must be finite/nonnegative, and their exact decimal sum must match the declared whole. More than 12 slices is unsupported; data is never truncated. Current V2.3 operation handlers do not generate this marker, so ordinary pipeline results without it return `unsupported` for pie eligibility. V2.2–V2.5 are not modified to manufacture evidence.

Unsupported semantics return `unsupported` with a structured reason. Missing values that prevent safe representation return `unsupported`; values that cannot be represented safely or contradictory pie evidence return a structured `failed` response.

## Data integrity and traceability

The backend copies the selected verified result rows into `VisualizationSpec.data` without changing labels, units, or values. SVG coordinates may be projected for display, but supplied values remain in the specification and are exposed as accessible labels/data attributes. No interpolation or analytical transformation occurs.

Each generated spec contains a unique visualization ID, chart type, axes, series, source step, data, metadata, and traceability for question, dataset ID, source operation, verification status, and correction status when applicable. Metadata records output row count, eligibility, and any rendering-order description. The current V2.2–V2.5 result schemas do not provide a common input-row-count field, so V2.6 reports it as unavailable rather than deriving it.

## Frontend

`VisualizationRenderer` dispatches through a fixed chart-type map to `BarRenderer`, `LineRenderer`, `PieRenderer`, or `ScatterRenderer`. Renderers use React and SVG primitives only. Backend data is parsed as JSON and rendered as text/geometry; it is never executed as HTML, JavaScript, or a renderer definition. The dashboard includes a JSON artifact-request panel so an existing V2.2–V2.5 response set can be submitted without adding another orchestration workflow.

## Errors

The API uses the contract categories: `invalid_visualization_input`, `unsupported_visualization`, `insufficient_data`, `invalid_visualization_schema`, `visualization_data_mismatch`, and `visualization_generation_failure`. Normal responses do not expose stack traces.

## Research boundary and limitations

V2.6 does not assess visualization quality or claim user preference or experimental improvements. The strict pie marker is not emitted by current upstream operation handlers; absent that evidence the correct result is unsupported. Chart selection rules are deterministic and may be revised only within the V2.6 contract boundaries.
