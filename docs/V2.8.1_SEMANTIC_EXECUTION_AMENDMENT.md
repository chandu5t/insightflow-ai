# InsightFlow AI V2.8.1 Semantic Execution Amendment

**Status:** research-owner approved implementation amendment  
**Version:** V2.8.1  
**Purpose:** freeze bounded deterministic execution semantics required by the V2.8 evaluation implementation. This amendment does not authorize or record official Step 7 experiment runs.

## 1. Research and benchmark invariants

The amendment changes execution semantics only. It does not change benchmark questions, ground truth, RQ1–RQ6, H1–H6, M1–M10, baselines, ablations, E1–E15, the error-injection schedule, or the statistical procedure. Runtime execution and V2.4 verification do not load or consult ground truth. Benchmark case IDs, question text, and expected answers are not inputs to operation dispatch.

V2.2 remains the plan/operation identity and validation boundary; V2.3 remains the controlled executor; V2.4 remains the independent verifier; V2.5 remains the existing bounded correction layer. No V2.5 eligibility or correction behavior is changed.

## 2. Trusted semantic manifests

The runtime accepts a manifest only for a repository-reviewed exact dataset snapshot whose SHA-256 is present in the versioned manifest registry. A manifest has these fields:

```text
manifest_version: non-empty version string
dataset_sha256: lowercase hexadecimal SHA-256 of exact dataset bytes
columns: map of exact physical column name to one allowed role
additive_products: explicit pairs of source column references whose product is additive
```

Allowed roles are `identifier`, `categorical`, `additive_measure`, `non_additive_measure`, `date`, `boolean`, and `unknown`. The manifest is trusted because its mapping is reviewed and shipped with the application and its SHA-256 must match the exact file bytes. Schema columns absent from the manifest have role `unknown`. Unrecognized snapshots have no manifest; operations that require semantic typing fail safely. A role is never inferred from a column name by itself, question text, benchmark ID, ground truth, or observed values.

### 2.1 Frozen snapshot mappings

For `module3_sales.csv` (SHA-256 `eae24ee4e675e8b99d6f0893a87c4b84717a0e2eb876a7f19654f88e46837d54`): `order_id=identifier`; `region`, `product`, and `category=categorical`; `order_date=date`; `quantity=additive_measure`; `unit_price=non_additive_measure`. The manifest explicitly authorizes the product of the `quantity` and `unit_price` columns as an additive measure.

For the exact frozen `module3_sales_direct.csv` snapshot (SHA-256 `520172097d69e40cf729714342d8d6ce7a7763670b5d13f6d673aaf1af0359cd`), the authoritative physical schema is:

| Physical column | Semantic role |
|---|---|
| `Order ID` | `identifier` |
| `Product Name` | `categorical` |
| `Quantity` | `additive_measure` |
| `Total Revenue` | `additive_measure` |
| `Region` | `categorical` |

This corrects the earlier manifest draft: the frozen CSV contains no `category` column, uses the exact physical header spellings above, and includes `Quantity`, which is explicitly approved as additive. Manifest lookup uses these physical header strings exactly. Header normalization, aliases, snake_case conversion, and any other implicit column-name mapping are prohibited. A name not present exactly in the manifest has role `unknown`. No other roles are inferred or added.

## 3. `filter_rows`

`parameters.conditions` is a non-empty list interpreted as AND. Each item is `{column, operator, value}` except `is_missing` and `is_not_missing`, which omit `value`. Operators are `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `in`, `not_in`, `is_missing`, and `is_not_missing`. `in` and `not_in` require a non-empty list. No OR, expression strings, coercion, `eval`, `exec`, SQL, or generated code is allowed.

Numeric comparisons require an explicitly numeric semantic role and numeric literals. Categorical/identifier/date equality and membership use exact string values. Ordered comparison on nonnumeric roles is rejected; ordered date comparison is unsupported because no date parsing/timezone grammar is frozen. Missing values satisfy only the explicit missing predicates and do not satisfy ordinary comparisons. Row order is preserved and rows are not deduplicated by predicate mode.

Exact duplicate removal requires explicit `mode="exact_duplicate_rows"` and `keep="first"`; it compares all columns and preserves first-occurrence order. It is never inferred from a question. Result is the filtered table with the source columns and row values.

## 4. `derive_metric`

The formula is a structured expression tree. Nodes are finite numeric literals (`{"literal": number}`), column references (`{"column": name}`), prior-step references (`{"step_id": id}`), unary negation (`{"op":"negate","value":expr}`), or binary `add`, `subtract`, `multiply`, and `divide` nodes with `left` and `right`. Formula column references must exactly match `PlanStep.inputs`; step references must be declared dependencies. Function calls, attributes, indexing, imports, arbitrary strings, code execution, and additional operators are invalid.

Required operands cannot be missing, nonnumeric, or nonfinite. Division by zero and nonfinite results fail structurally. Vector results preserve row alignment. Results carry semantic role and lineage. Only the manifest-authorized `quantity × unit_price` product is assigned additive role by the sales manifest; other products are `unknown` unless independently authorized by a manifest. A derived result can be aggregated only when its recorded role is `additive_measure`.

## 5. `group_by` and `aggregate`

Missing group keys are represented by the deterministic group label `(missing)`; values are not imputed. Groups are emitted in sorted key order. If a literal `(missing)` key coexists with missing values, execution fails rather than merging distinct source values. Existing non-missing grouping behavior remains unchanged. No ranking tie behavior is introduced.

`aggregate` supports `function="sum"` only and exactly one input value. Scalar aggregation consumes an additive-measure source column or additive derived series. Grouped aggregation consumes the explicit group result and emits sorted `{key,value}` entries. Identifiers, non-additive measures, unknown roles, and untrusted snapshots fail safely. Missing, invalid, or nonfinite values fail; empty scalar or grouped input is unsupported. Mean, median, min, max, and other reducers are not supported.

Output is either `{kind:"scalar", value:number}` or `{kind:"grouped", groups:[{key:string,value:number},...]}`. Numeric results must be finite.

## 6. `calculate_percentage_difference`

Given dependencies in plan order as `value` then `reference_value`, compute exactly:

```text
((value - reference_value) / reference_value) * 100
```

Both operands and result must be finite numeric scalars. A zero reference is a structured failure. The output unit is percentage points. The reference is not made absolute.

## 7. `compare_groups`

The operation performs no ranking. Parameters are:

```text
left:  {step_id:string, selector:"scalar" | {kind:"group_key",key:string}
        | {kind:"list_item",index:nonnegative_integer,field:string}
        | {kind:"leader"}, multiplier:finite_number}
comparator: "lt" | "lte" | "eq" | "gte" | "gt"
right: same structure as left
```

Each `step_id` must be declared in `depends_on` and identify a successful Analysis Agent result. `scalar` selects a numeric scalar (including the value member of a scalar aggregate); `group_key` selects one uniquely matching grouped aggregate entry; `list_item` selects an explicit field from a successful rank/top_n/bottom_n result; `leader` selects the first value only from a successful rank/top_n result. No tie resolution is performed by compare_groups. References that are absent, ambiguous, nonnumeric, nonfinite, or not from a successful step fail safely.

Compute `left_value * left_multiplier comparator right_value * right_multiplier`. Output is `{left_value:number, comparator:string, right_value:number, result:boolean}`; the left/right fields are the multiplier-adjusted operands. No natural-language expression parsing is allowed.

## 8. V2.4 independent verification

V2.4 independently recomputes each completed V2.8.1 operation from the exact dataset snapshot, its trusted manifest where required, the validated plan, operation parameters, successful dependency outputs, and recorded lineage. It does not call the V2.3 executor as its expected-value calculation and never reads ground truth. Filter/group/table outputs are compared structurally; numeric values use V2.4's existing fixed absolute tolerance `1e-9` and zero relative tolerance; Boolean comparisons are exact.

Missing semantic metadata, unavailable dependencies/lineage, unsupported date ordering, or otherwise insufficient evidence yields `unsupported` with `verification_semantics_undefined`. A deterministic mismatch yields `failed` with `numerical_mismatch` (or the applicable structured schema/failure category). A verifier exception is a structured `verification_failure`, not a silent pass. Checks record operation, evidence references, manifest version, expected and observed result, and tolerance where applicable. No ground-truth data is required or available to the verifier.
