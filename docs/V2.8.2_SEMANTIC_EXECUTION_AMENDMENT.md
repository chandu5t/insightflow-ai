# InsightFlow AI V2.8.2 Semantic Execution Amendment

**Status:** approved semantic decisions; implementation not yet authorized by this document
**Version:** V2.8.2
**Supersedes:** none; V2.8.1 remains immutable and applicable to its own source revision
**Purpose:** freeze deterministic ordered-date filtering, grouped row-count, and trusted metric-definition context for a later implementation step. This amendment does not authorize official Step 7 execution.

## 1. Research and benchmark invariants

This amendment defines execution and verification semantics only. It does not modify benchmark questions, ground truth, datasets, RQ1–RQ6, H1–H6, M1–M10, baseline or ablation definitions, E1–E15, error-injection schedule, or the statistical procedure. Runtime planning, execution, and V2.4 verification must not load, consult, or infer from ground truth. Runtime logic must not branch on benchmark case IDs, question records, or expected answers.

The V1 workflow and APIs remain unchanged. V2.2 remains the plan and validation boundary; V2.3 remains the controlled execution boundary; V2.4 remains the independent verification boundary; V2.5 remains unchanged, including its strategy, eligibility conditions, correction budget, and terminal behavior. The existing V2.8.1 amendment and its freeze record are immutable. A distinct V2.8.2 Step 7 freeze record is required before any official rerun.

## 2. Ordered date predicates

### 2.1 Eligibility and representation

An ordered date predicate is permitted only when the referenced physical dataset column has trusted semantic role `date` under the exact dataset snapshot's trusted semantic manifest. Column names, question text, and observed values do not establish this role.

Date literals and non-missing source values MUST use the exact date-only representation `YYYY-MM-DD`, with four-digit year and two-digit month and day. Parsing MUST be strict and calendar-valid. Timestamps, timezone conversion, locale-specific formats, whitespace trimming, implicit coercion, and format inference are prohibited. No new predicate operators are introduced.

The existing `lt`, `lte`, `gt`, and `gte` operators compare parsed calendar dates only. Existing `eq`/`ne`/membership behavior is unchanged by this section. Ordered predicates on columns without trusted `date` role remain invalid/unsupported under the existing safe-failure boundary.

### 2.2 Boundary translation

- “On or before D” MUST be represented as `lte D`.
- “From D1 through D2 inclusive” MUST be represented as the conjunction `gte D1` AND `lte D2`.
- A calendar month MUST be represented as the half-open interval from its first day inclusive to the first day of the next calendar month exclusive. January 2025 is `gte 2025-01-01` AND `lt 2025-02-01`.
- The existing `filter_rows` conjunction semantics apply. There is no `between`, month, or other new operator.
- A range whose parsed start is later than its parsed end MUST fail V2.2 plan validation with an invalid-range validation error. A malformed or impossible date literal MUST fail V2.2 plan validation with an invalid-date-literal validation error. Neither may reach V2.3 execution.

### 2.3 Invalid and missing values

Malformed or impossible date literals MUST fail validation. A non-missing source value that does not strictly parse as `YYYY-MM-DD` MUST cause the operation to fail; it MUST NOT be silently discarded, coerced, or treated as missing. A missing source date does not satisfy any ordered date predicate and is not an operation error. It may be selected only by the existing explicit `is_missing` predicate.

V2.3 MUST return a structured `agent_failure` for a non-missing source date that fails strict parsing and MUST NOT return partial filtered data. The failed step remains failed under the existing workflow status model.

## 3. Grouped row count

`group_by` followed by `count` means the number of source rows in each group. It does not mean the number of groups, the number of unique values, or the number of non-null values in a field.

A grouped `count` step MUST declare exactly one dependency, and that dependency MUST identify a successfully completed `group_by` step. The grouped count MUST count every row in each group. Rows placed by `group_by` in the existing `(missing)` group MUST be counted there. Group entries MUST preserve the deterministic sorted key order produced by `group_by`.

The result schema is exactly:

```json
{"kind":"grouped_count","groups":[{"key":"string","value":0}]}
```

Each `key` is a string and each `value` is a non-negative integer row count. An empty grouped input produces `{"kind":"grouped_count","groups":[]}`. A malformed dependency, unsuccessful dependency, or non-group result MUST fail structurally; no implicit grouping or source-field inference is permitted.

This section does not change root/raw dataset row count and does not define `count(column)`. Those remain governed by their existing contracts.

## 4. Authoritative metric-definition registry

### 4.1 Trust and purpose

The application MUST maintain a versioned, project-owned registry of metric definitions. Registry entries are selected by the exact dataset SHA-256, metric key, definition version, and semantic-manifest version. They are application-owned trusted context; arbitrary client-provided text, question text, retrieved passages, benchmark annotations, or model output cannot create or override an entry.

The registry MUST NOT contain or depend on benchmark IDs, benchmark questions, ground truth, expected answers, or observed benchmark results. Dataset snapshot hashes and exact physical column names are permitted because they bind definitions to reviewed data schemas and are not benchmark-case identifiers.

### 4.2 Entry schema

Each registry entry MUST provide these fields:

```text
dataset_sha256: lowercase hexadecimal SHA-256 of exact dataset bytes
metric_key: stable project-owned metric identifier
definition_version: non-empty immutable version identifier
manifest_version: exact trusted semantic-manifest version
display_name: human-readable metric name
exact_column_references: list of exact physical CSV headers referenced
allowed_expression: validated structured expression using only the V2.8.1 derive_metric grammar
output_semantic_role: one allowed semantic role
source_reference: project-owned document/module and source revision or content digest
```

The registry MUST reject entries whose dataset hash, manifest version, physical columns, expression references, or output role do not agree with the trusted dataset semantic manifest. It MUST reject implicit aliases, header normalization, snake-case conversion, and inferred columns.

### 4.3 Frozen revenue entries

For the exact frozen `module3_sales.csv` snapshot, `revenue` is defined as the structured expression `quantity × unit_price`, with exact physical references `quantity` and `unit_price`, output role `additive_measure`, and the already approved manifest binding.

For the exact frozen `module3_sales_direct.csv` snapshot, `revenue` is defined as a direct reference to the exact physical column `Total Revenue`, with output role `additive_measure` and the already approved manifest binding. This is a direct metric reference; it MUST NOT be rewritten to a normalized alias or inferred from the header.

The registry source metadata MUST cite the existing project-owned revenue rule (including `backend/app/tools/revenue.py`) and the exact snapshot/manifest binding. The registry is a V2 planner-context source; it does not invoke or alter V1 execution behavior.

### 4.4 Planner context boundary

Before planning, the application orchestration layer MAY obtain exact physical schema from the existing dataset repository/loading abstraction and MUST obtain metric definitions only from the validated registry. It MUST validate that the dataset bytes match the trusted snapshot/manifest before passing registry-backed context. The V2.2 planner itself MUST NOT load datasets, access PostgreSQL/pgvector, perform retrieval, calculate values, or execute plans.

Planner context is limited to:

1. exact physical column names for the selected dataset;
2. trusted semantic roles for those exact columns;
3. registry-backed metric key/name, definition version, manifest version, exact column references, allowed structured expression, output semantic role, and source reference.

Planner context MUST NOT include case IDs, benchmark question records, ground truth, expected values, runtime answers, or unrelated dataset rows/values. Registry-backed structured expressions are authoritative constraints: the generated plan MUST use the selected allowed expression exactly for the registry-defined metric. An absent, mismatched, or untrusted definition MUST result in a structured unsupported plan or other existing safe failure; the planner MUST NOT invent a formula.

## 5. V2.4 independent verification

V2.4 MUST independently verify these added semantics without loading ground truth and without treating V2.3 output as the expected-value calculation.

### 5.1 Ordered date filtering

The verifier MUST use the same exact dataset snapshot, trusted manifest, validated predicate, and strict date grammar as the contract. It MUST independently apply the date predicate and compare the complete filtered table using the existing structural-comparison policy. Missing dates do not match ordered predicates. A malformed literal or reversed range is an invalid plan and therefore is rejected by V2.2 before execution; V2.4 MUST NOT independently repair or reinterpret it. If V2.3 records the filter step as failed because a non-missing source date is invalid, V2.4 MUST preserve the failed execution/status evidence and MUST NOT mark that operation numerically verified. If a purported completed filter result is supplied despite such an invalid source date, V2.4 MUST fail the `date_data_validity` consistency check with category `consistency_violation`. Invalid date data MUST NOT be silently skipped or treated as a pass.

### 5.2 Grouped count

For a `count` step with exactly one successful `group_by` dependency, the verifier MUST independently derive the group key for each source row using the validated grouping column and existing trusted missing-key policy, count rows per key, sort keys deterministically, and compare the complete expected `grouped_count` structure exactly with the observed structured result. It MUST verify the dependency identity/status and operation metadata. Missing dataset context or untrusted schema/manifest produces unsupported verification; structural or value disagreement produces failed verification. Ground truth is never consulted.

### 5.3 Registry-backed metrics

For a registry-backed metric expression, the verifier MUST validate the registry binding against the exact dataset SHA-256 and manifest, independently calculate from the allowed expression and source data, and compare results using the existing V2.4 numeric tolerance: absolute `1e-9`, relative `0.0`. It MUST record registry/manifest versions, source-column references, expression/lineage evidence, and expected/observed structured values. Missing or mismatched trusted metadata produces unsupported or structured failure as appropriate; it never falls back to ground truth or model interpretation.

Existing V2.4 status precedence, categories, result schema, independent-verification boundary, and all unrelated verification rules remain unchanged. Any necessary new check detail must be additive and structured.

## 6. V2.5 unchanged

No V2.5 semantic or implementation change is authorized. In particular, the sole strategy `reconcile_single_step_id_mismatch`, its exact eligibility evidence, correction target, 0–2 budget, initial-only unsupported exception, terminal statuses, and V2.2 → V2.3 → V2.4 correction flow remain unchanged. A new grouped-count/date/metric result is not a new correction eligibility condition.
