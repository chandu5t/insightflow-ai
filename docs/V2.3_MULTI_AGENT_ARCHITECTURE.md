# V2.3 Multi-Agent Architecture

## Scope

V2.3 accepts `question`, `dataset_id`, and a V2.2 `AnalysisPlan`, checks that plan with the existing V2.2 validator, and runs a separate sequential LangGraph workflow. It adds `POST /analysis/multi-agent`; the V1 `POST /analysis/query` route and graph remain separate. The planner does not run inside the V2.3 endpoint, and V2.3 does not change or repair the plan.

## Workflow

1. The Data Understanding Agent loads dataset metadata and the cleaned CSV through the existing `DatasetRepository` and `load_dataframe` abstractions. It returns columns and basic shape context.
2. The Supervisor takes plan steps in their existing order and resolves each operation through the deterministic V2.2-operation-to-agent table. `inputs` names operation data/values; only `depends_on` is resolved as prior step IDs.
3. All 14 V2.2 operations map to the registered `analysis` agent. The Analysis Agent uses controlled handlers and passes raw intermediate values only within the graph state.
4. For a `metric_definition` intent, the Supervisor invokes the Knowledge Agent after dataset preparation. The Knowledge Agent uses the existing `MetricRetriever`; it is not invoked for other intents.
5. The graph returns a structured `MultiAgentResult` containing status, executed step IDs, agent results, final result, and errors.

The agent registry contains exactly `data_understanding`, `analysis`, and `knowledge`. No model selects an agent. The LangGraph is sequential and independent of the V1 classifier/execute/validate/explain graph.

## Contracts and errors

`MultiAgentRequest` has `question`, UUID `dataset_id`, and `analysis_plan`. `WorkflowState` records question, dataset ID, plan, current step, completed steps, step results, agent outputs, status, and errors. `AgentResult` records agent, optional step ID, status, result, metadata, and error.

The API reruns the existing structural plan validator at the boundary. Invalid plans return a failed workflow result with `invalid_plan`; unknown routes, agent failures, workflow failures, and invalid state have structured error categories. Agent failure terminates the run; there is no retry, correction, or replanning.

## Controlled operation semantics

The V2.2 registry remains authoritative for operation names and metadata. In this implementation, `select_columns`, `group_by`, `sort`, `top_n`, `bottom_n`, row `count` without a column, `distinct_count`, and `calculate_difference` have controlled execution paths; `rank` runs only when the values have no ties. Grouping, sorting/ranking, and distinct counting also fail safely when missing-value semantics would affect the result. These paths require the input shapes documented by the registry and dependencies supplied through `depends_on`.

V2.2 does not sufficiently define predicate grammar for `filter_rows.conditions`, a safe formula grammar for `derive_metric.formula`, supported function values for `aggregate`, `count(column)` null/value semantics, missing-value behavior for grouping/sorting/distinct count, tie behavior for `rank`, a denominator convention for `calculate_percentage_difference`, or the measure/semantics for `compare_groups`. Those cases return structured operation failures. V2.3 does not guess or reinterpret them. Invalid inputs to otherwise supported handlers also return structured failures. No arbitrary Python, shell, imports, or unrestricted database execution is used.

The workflow state tracks each plan step through `pending`, `running`, `completed`, or `failed`. Unexpected graph construction/invocation errors return a structured `workflow_failure` without retrying.

Intermediate DataFrames are held only inside workflow state and are returned as plain structured records. There is no new persistence schema. Knowledge retrieval is injected through the existing metric-retrieval interface.

## Phase boundaries

V2.3 ends after controlled execution and result collection. It does not verify result correctness, independently recompute results, self-correct, retry failed reasoning, replan, visualize, or perform benchmark evaluation. Existing V1 result validation/grounding nodes are not reused in this graph.
